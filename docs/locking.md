# PostgreSQL locking

PostgreSQL MVCC lets ordinary readers see a committed snapshot while writers change rows. Readers usually do not block writers, and writers usually do not block readers, but both can contend on row locks. DDL also takes table locks. `ALTER TABLE ... ADD COLUMN`, `SET NOT NULL`, and dropping columns require an `ACCESS EXCLUSIVE` lock at some point. The runner uses a two-second `lock_timeout` so an operation fails for operator retry instead of queueing behind a long transaction. A two-minute statement timeout bounds transactional schema changes; concurrent index creation uses a longer statement bound.

The session-level advisory lock serializes migration operators; it does not lock `customers` or freeze app traffic. Backfill transactions select bounded rows using `FOR UPDATE SKIP LOCKED`; they hold row locks only until the batch commits. `SKIP LOCKED` distributes work but an empty batch is not proof of completion if other workers hold rows. The worker rechecks eligible rows and exits only when none remain outside quarantine. Keep transactions short because long snapshots delay vacuum and extend lock interactions.

The tenant/email index is created with `CREATE INDEX CONCURRENTLY` outside a transaction. It permits ordinary inserts, updates, and deletes during the build, but performs multiple scans and waits for relevant transactions. A failed build can leave an object whose `pg_index.indisvalid` is false. The runner detects that state, drops it concurrently, retries, and checks validity afterward. The check constraint is added `NOT VALID` so its initial installation avoids scanning all historical rows; new writes are checked immediately. `VALIDATE CONSTRAINT` scans existing rows with a less restrictive lock. `SET NOT NULL` may still need a short exclusive lock, and can fail on timeout. The 2-second bound applies to lock acquisition, not total run time.

The integration test uses a real transaction holding a conflicting table lock, verifies that DDL returns PostgreSQL SQLSTATE `55P03`, and confirms that an ordinary read can still complete. This is a bounded test of one lock scenario, not proof that every workload will avoid waits. The dashboard samples `pg_stat_activity` and `pg_locks`; an observed waiter is not by itself evidence that customer requests were blocked.
